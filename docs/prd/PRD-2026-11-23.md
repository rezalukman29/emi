## 1. Product in one paragraph

EMI is a multi-tenant SaaS for event-decoration companies (weddings, galas, corporate events). A tenant manages its
item catalog and stock per warehouse, plans **events** (which items go to which area of the venue), moves each event
through a **configurable stage pipeline** (prepare → scan in → event running → scan out → return/check), and gets items
it does not own through **Production** (becomes our asset), **Rent** and **Outsource** (temporary, never our asset).
Around that: an **Event Checklist** for the crew, an **Event Calendar** with item clashes, reports and a SaaS Owner panel.

## 4. Events

### 4.1 Event list (`/event`)
- Tabs by **lifecycle** from the server: Upcoming, On Going, Ready to Close (`ready-to-close`), Ready for Checking
  (`checking-inventory`), Returned & Completed, Transferred, and Invite. Summary cards: active = upcoming + on-going +
  ready-to-close; completed = returned-completed + transferred. **[RULE]** Tabs and counts come from `/v2/event-filter?status=`; the web does not
  move events between tabs itself.
- **[RULE]** The open tab is remembered (URL `?tab=` + browser tab session): Back to Events returns to it.
- Card: cover photo (if the event has one), name, dates, item count, chip **Overdue · N d** when the finish date has
  passed but the event is still open, **In progress** while running. Whole card opens Event Detail.
- Icons: History → Event History; Edit (disabled after the event ended); Delete.
- **[RULE] Delete:** an event with items (or unknown count) requires typing the event name (not case-sensitive);
  an event with 0 items uses a normal confirm.
- **[QUESTION]** What happens to items, stock and scans when an event with items is deleted? Should the server refuse?
- **[NEEDS API]** **Overdue tab** + **[QUESTION]** should overdue events leave Upcoming/On Going or show in both?

### 4.2 New / Edit event
- **PIC** is picked from the tenant's users and saved as the user's **name** (API field unchanged). Older free-text
  PIC values stay selectable. **[QUESTION]** Should PIC become a user id (follow renames, "my events")?
- **[RULE]** Finish date ≥ start date. Rich text for Description / Note: **[QUESTION]** option A/B/C (B = Markdown recommended).

### 4.3 Event Detail (`/event-detail?id=`)
- Two layouts in an **A/B test** (admins switch with the floating switcher; per browser):
  - **A** = original. **B** = hero card (dates, venue, PIC, code, current stage + next action + hint), stat tiles
    (Items, Scanned in / Checked, Scanned out, Checklist), Items / Event Checklist tabs, search + one Filter + view toggle.
  - **[QUESTION]** Which version wins? After the decision the other layout is removed.
- Stage pipeline: stages and their rules come from **Event Settings** (scan, cut stock, stock return, production,
  rent, outsource, ownership check, allow delete, allow add item). **[RULE]** Never hard-code stage names.
- Header / ⋯ menu: Add Item, Outsource Item, Rent Item, Request Production, Files, History, Summary, Rentals,
  Group Items, Bulk Assign Ownership, Cross Check, Print… (Print Plan or This page).
- Item drawer: Qty / Status / Ownership, Location, Progress (Checking, Scan In, Scan Out); Remove, Go to item detail,
  ⋯ (Modify, Report broken, Create production, Scan).

### 4.4 Add Items from Inventory (modal) — A/B test
- **[RULE]** Tabs **Available / Out of Stock**: an item is available when **any** warehouse has stock > 0.
  Counts cover the items loaded so far ("+" = more pages). **[NEEDS API, optional]** exact counts.
- **[RULE]** A warehouse is pre-selected: the one with the **most stock** for that item.
- Version **B**: one row per item with stock colour (green / orange < 10 / red 0), − qty + stepper, "N in cart",
  out-of-stock rows offer **Rent Item / Request Production** (only when the stage allows), phone Browse / Cart switch.
- **[QUESTION]** May a user add more than the warehouse stock (and rent/produce the rest later), or must the server refuse?
  The web does not block it in the picker; this PRD does not know what the server does.

### 4.5 Event History (`/event-history?id=`) — [PREVIEW] dummy data, [NEEDS API]

Search + type filter. Real data needs the activity log API (`docs/api-backlog.md` §2).

## 5. Event Checklist — [PREVIEW], [NEEDS API]

Full decision record: `docs/prd/event-checklist.md` (Round 3). Summary of the current rules:

- **One checklist per event**, organised in **free groups** (not tied to stages). Templates are groups of tasks;
  every new event gets a copy (copy, not link). Shown on the Event Checklist page and in Event Detail (same data).
- **Task:** title, group, required yes/no, **needs photo**, **needs report**, due date, **assigned user**,
  status To do / Done / N/A / Issue, photos, report/note, history.
- **[RULE]** A task that needs a photo / report can only be ticked through the *Complete task* form with that proof.
- **[RULE]** Unticking is allowed; photos and report stay; the history records it. Nothing in the history is deleted.
- **[RULE]** When a task is ticked and the setting is on (every task / required only), **all admins** of the tenant get an
  e-mail. Preview: only listed, not sent.
- **[RULE]** A group can be signed off (supervisor / client / both, optional drawn signature) when its required tasks
  are resolved and no issue is open; it can then be locked; admins can reopen.
- Filters: All / Not done / Done, Assigned to me; event list "needs attention" and "tasks for me".
- **[QUESTION]** Should required tasks block moving the event to the next stage (v1 did; v3 groups are free)?
- **[QUESTION]** Should the assigned user also get a notification? Who else besides admins (e.g. the event PIC)?

## 6. Production, Rent, Outsource (unchanged business rules)

- **[RULE]** Production Done → quantity becomes our stock (asset).
- **[RULE]** Rent = we rent from a vendor; returned; never our stock or asset. Outsource works like Rent (own vendors).
